# ARTEX 侵害指標 (機械可読)

日本語 · [English](README.md)

ARTEX が自ら発する固有のフィンガープリントを 1 つのファイルにまとめた、機械可読なリストです。検知ロジックではなく
アトミックな指標そのものを求める防御者向けです。[`artex_indicators.csv`](artex_indicators.csv)を
脅威インテリジェンスプラットフォームや SIEM のルックアップテーブル、ホストのトリアージ(triage)チェックリストにそのまま投入してください。
すべての値は、このリポジトリのソースで確認した文字列です。[検知ルール](../README.ko.md)と防御ガイド
([韓国語](../../docs/defense-ko.md) · [English](../../docs/defense-en.md) 2 節)が根拠としている、まさに
その文字列です。各行には、その値がどこから来るのかと、(あれば)その上に構築したルールを記載しています。

## 列構成

- **`id`**: 指標の安定したスラッグです。
- **`type`**: 指標の種類です: `http.user-agent`、`string`(ログ・ファイルから探すリテラル)、`port`、
  `ip-dst|port`、`other`(上記の分類に当てはまらないホストアーティファクト。例: データベーススキーマのオブジェクト名)。
  これらは対応する MISP/STIX の属性タイプにマッピングされます。
- **`value`**: 正確な指標です。非 ASCII のガードマーカーを含め、原文のまま保存しています。
- **`perspective`**: `target`(ARTEX が探査するシステムに*向かう*通信で観測)または
  `forensic`(ARTEX が実行された、または経由したホスト*上*で観測)です。防御ガイドはこの 2 つを意図的に
  区別しています。混ぜると誤った結論になります。
- **`source`**: その値を発する、リポジトリ基準の相対パスのソースファイルです(`;` 区切り)。これが
  根拠です: アップストリームの再同期で出力側が変わった場合は、ここの指標も一緒に変える必要があります。
- **`rule`**: その正確な値の上に構築した検知ルールです(`;` 区切り)。(ノイズの多い)ルールとして出力せず
  直接トリアージするホストフォレンジック指標は空です。
- **`description`**: 1 行の説明で、該当する場合は正直な注意点を併記します。

## MISP イベントのエクスポート

同じ指標をそのままインポートできる [MISP](https://www.misp-project.org/) イベント
[`artex_indicators.misp.json`](artex_indicators.misp.json)としても提供しています。MISP インスタンスを運用している
(または MISP 形式を取り込む脅威インテリジェンスプラットフォームを使っている)防御者は、CSV の列を手作業でマッピングせずに
フィンガープリントをそのままインポートできます。STIX 2.1 は MISP 自身のコンバーターで一度エクスポートすればよいため、
リポジトリが損失のある 2 つ目の形式を別途作ることはありません。

- **タイプのマッピング。** 各 CSV `type` は対応する MISP 属性タイプになります: `http.user-agent` →
  `user-agent`、ガードマーカー `string` → `pattern-in-file`(カテゴリ *Artifacts dropped*)、`port` →
  `port`、`ip-dst|port` → `ip-dst|port`(複合値は MISP の `ip|port` 形式を使うため、`127.0.0.1:8788`
  は `127.0.0.1|8788` として保存されます)、探索グラフスキーマのフィンガープリント `other` → `other`(カテゴリ *Other*)。
- **`to_ids` は `rule` 列に正直に従います。** 検知ルールが構築されている行は対処可能な指標なので
  `to_ids: true` とします。ルールがないホストフォレンジック行(既定の待ち受けポートとループバックプロキシの
  エンドポイント、および探索グラフスキーマのフィンガープリント)は、ブロック用 IoC ではなくトリアージのヒントなので
  `to_ids: false` かつ `disable_correlation: true` とします(一般的なポートや `127.0.0.1`、あるいは汎用的なテーブル
  名が MISP の相関を汚染してはなりません)。これは CSV の `rule` 列と以下の注意点がすでに含んでいるものと
  同じ区別です。
- **インポート。** [pymisp](https://github.com/MISP/PyMISP)で
  `MISPEvent().load_file("artex_indicators.misp.json")`、または *Add event → Populate from … → MISP
  format* UI、あるいは REST API でインポートします。イベントは未公開状態で、`tlp:clear` タグが付いて
  います。インポート時にインスタンスに合った配布範囲と公開状態を設定してください。

## このリストを正直に読む方法

- **これらは変更可能なフィンガープリントであり、安全の証明ではありません。** オペレーターが User-Agent を別の値に
  設定したり、既定のポートを変更したりできるため、ここにある値が*ない*からといって ARTEX がないという意味では
  **ありません**。長持ちするシグナルは行動です。相関ルールと防御ガイドの 1・2・4.1~4.2 節を参照してください。
- **汎用的なハンティングの手がかりは意図的に除外しました。** 破壊的なシェル・DB コマンド(`rm -rf`、`DROP DATABASE`、…)は ARTEX の
  フィンガープリントでは*ありません*。正当な管理者も実行します。インポート用の指標ではなくハンティングの手がかりなので、この
  リストではなく [`destructive_command_hunting.yml`](../sigma/destructive_command_hunting.yml)と防御
  ガイドに置いています。これらをブロック用指標としてインポートすると誤検知が発生します。
- **norma の WebFetch User-Agent はネットワーク署名であり、インポート用のアトミック指標ではありません。** ワーカーの
  ページ取得ツールは攻撃段階で `norma/0.4` を送信し、Suricata ルール sid 1000003 が `norma/`
  プレフィックスで発火しますが、その文字列は norma SDK にハードコードされた独自の User-Agent(`github.com/Autumn-27/norma/tool/webfetch.go`)で、
  norma 上に構築されたすべてのツールが同じように発する値であり、ARTEX 固有のフィンガープリントではありません。この値をブロック用
  指標としてこのリストに入れると、すべての norma SDK 通信でアラートが鳴ります。これは破壊的コマンドを除外したのと同じ
  誤検知の罠です。そのため norma UA はこのリストから意図的に除外し、ネットワークルールとしてのみ掲載しています
  ([`../suricata/README.ko.md`](../suricata/README.ko.md)、sid 1000003)。また、この値はこのリポジトリの
  ソースではなく固定された依存関係(`github.com/Autumn-27/norma`)に根拠を置いているため、後述の根拠テストが
  ARTEX 自身が発する文字列を読み直すのと同じようには、この値を読み直せません。
- **ホストフォレンジックのポートはブロックではなくトリアージ用です。** `:8787` と `127.0.0.1:8788` は ARTEX を
  実行している可能性のあるホストを指します。`ss`・`netstat` で確認し、闇雲にファイアウォールで
  遮断しないでください。
- **探索グラフスキーマのフィンガープリントはネットワーク・ファイルの IoC ではなく DB 調査用です。** `exploration_nodes`
  テーブルは、ARTEX が PostgreSQL に置く探索グラフの中核テーブルです。単独のヒットで断定
  せず、兄弟テーブル(`exploration_edges`・`exploration_anchors`・`assets`・`companies`・`activity`)と
  `agent_prompts` シードが同じデータベースに共存しているかで確認してください。オペレーターがテーブルを変更したり
  削除したりできるため、不在が安全を意味するわけではありません。
- **`rule` が空のホスト・DB 行には実行手段があります。** Sigma ルールとして掲載せず直接トリアージする 3 つの
  指標、すなわち待ち受けポート・記録プロキシのエンドポイント・このスキーマのフィンガープリントは、[ホストトリアージスクリプト](../triage/)が不審な
  ホストですべて点検します。そのため、シェルアクセスはあるが SIEM がない対応者が `ss`・`netstat`・`psql`
  を手作業で実行する必要はありません。

## 検証

このリストは[指標の根拠(source-of-truth)テスト](../tests/indicators/run.sh)でカバーされています。この CSV を再度
読み込み、すべての行について、その値が引用したソースファイルに今もあり、引用したルールに固定されているか、そして
テストが根拠とするすべての指標がリストに現れているかをアサートします。ソースと食い違う行や、リストから漏れた
既知のフィンガープリントがあれば、テストは失敗します。次のように実行してください。

```sh
detections/tests/indicators/run.sh
```

MISP イベントは独自の [MISP エクスポート整合性テスト](../tests/misp/run.sh)でカバーされています。イベントを pymisp
で読み込み(すべての属性タイプがサーバーの受け入れる実在の MISP タイプになるように)、この CSV と行単位で
同期していることをアサートします。つまり、同じ値、意図したタイプ・カテゴリ、そして `rule` 列に合わせた `to_ids` フラグです。
イベントは CSV と並べて手作業で管理しています。CSV が持たない、属性ごとに整理した注釈・安定した
UUID・イベントレベルのタグも保持しているため、損失のある既定値でこれらを上書きするジェネレーターはありません。
CSV の行を追加・削除したりタイプを変更したりする場合は、同じコミットで
[`artex_indicators.misp.json`](artex_indicators.misp.json)も合わせて修正してください(新しい属性には新しい `uuid` と
根拠となる `comment` を付けてください)。両者が一致するまでこのテストは失敗するため、更新を黙って忘れる
ことはできません。次のように実行してください。

```sh
detections/tests/misp/run.sh
```
