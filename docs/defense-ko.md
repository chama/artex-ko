# 自律型AI攻撃の防御・検知ガイド

> この文書は、ARTEX のような**自律型AI侵入エージェント**がどのように動作するかを防御側の立場で理解し、その攻撃を**検知・遮断する能力**を養うための資料です。攻撃方法を案内する文書ではありません。すべての内容は、自分が所有している、または書面で明示的な許可を得たシステムを守る目的にのみ使用してください。権限なく他人の情報通信網を点検・攻撃する行為は、それ自体が犯罪です([上位 README のセキュリティ・悪用に関する警告](../README.md)を参照)。
>
> English: **[Defense and Detection Guide (defense-en.md)](defense-en.md)**.

自律型AI攻撃ツールは、人が一人付きっきりで手動実施していたペネトレーションテストを、LLM エージェントが**自ら目標を分解し、実際のツールを実行しながら発見を蓄積する** 24 時間の自動プロセスに変えます。防御側が対峙する相手は、「熟練した攻撃者一人」から「疲れず休まないエージェント群」に変わるわけです。このガイドは、その変化が検知・対応に何を求めるかを整理します。

---

## 1. 自律型AI攻撃は従来のスキャナと何が違うのか

従来の脆弱性スキャナ(例: 固定シグネチャベースのツール)は、あらかじめ決められた点検項目を順番に投げて終わりです。ARTEX 系の自律エージェントは構造が異なります。[システムアーキテクチャ](../README.md#システムアーキテクチャ)で説明されているとおり、次の要素が組み合わさって**人の介入なしに複数段階の攻撃チェーンを完遂**します。

- **役割が分かれたマルチエージェント。** 目標を分解する `goals`、次の方向を判定して意図(intent)を出す `planner`、意図一つを実際のツールで実行する複数の `worker`、人が介入する `mainagent` に分かれます。planner が唯一の意図生成者で、worker がその意図を並列に実行します。
- **二重グラフに状態を蓄積。** 「何があるか」(資産グラフ)と「どこまでテストしたか」(探索グラフ)を別々に積み上げ、アンカーで結びます。そのため攻撃が**段階的に深まり**、同じ資産を別の角度から再訪し、先行する観測の上に次の段階を組み立てます。
- **イベント駆動の閉ループ。** グラフが変わるたびに planner が起動して次の意図を割り当て、worker の書き込みが再び次のラウンドを引き起こします。目標が証明されるまで、この循環は止まりません。
- **直列の攻撃チェーンを安定して進行。** planner は「注入点の発見 → 認証情報の取得 → 横展開 → 権限昇格」のような依存順序を共有 todolist に一度だけ記録し、先行段階が満たされた次の段階にのみ意図を割り当てます。そのため、ステートレスなセッション環境でも攻撃チェーンが乱れずに完遂されます。
- **LLM が文脈ごとにペイロードを変形。** 実行ツールとペイロードがコードに固定された定数ではなく、LLM が状況を読んで生成する値なので、リクエスト一つ一つの形が少しずつ異なります。

### なぜ検知がより難しいのか

- **固定シグネチャが当たりにくくなります。** ペイロードが文脈ごとに変わるため、既知の悪意ある文字列を厳密に一致させる方式のルール(WAF シグネチャ)はすり抜けやすくなります。
- **ゆっくり、しかも人間らしく区切って進められます。** エージェントはラウンドの間に休み、発見に応じて方向を変えるため、単に「短時間に大量のリクエスト」だけを見るレートベースの検知では見逃すことがあります。
- **偵察と侵入が一つの流れでつながります。** 人が偵察結果を見て数日後に手動で攻撃していた間隙がなくなり、最初の接触から資料持ち出しまでの時間が大幅に短くなります。

### それでも検知できる理由: 行動は隠しにくい

静的な指紋(User-Agent、特定のペイロード文字列)は、運営者がその気になれば変更できます。しかし**自律エージェントの行動様式**は攻撃の本質なので、変えるのが困難です。以下の第 2〜4 節は、この行動ベースの観点に重きを置いています。

- 一つの発信元が**複数段階の性質の異なるリクエスト**(偵察 → 列挙 → 認証試行 → エクスプロイト)を**一貫したセッションとしてつなげていく**パターン。
- 人間なら疲れて止まる時間帯にも**途切れなく続く**探索。
- 失敗した応答からヒントを得て**次のリクエストを体系的に変形する**、無作為ではない適応的な進行。

## 2. 防御側が観測できる指紋(IoC・シグネチャ)

指紋を二つの観点に分けて見ます。**(ア)対象(被攻撃者)の観点**は、自分のシステムに向けられた ARTEX トラフィックから見えるものです。**(イ)運営者・フォレンジックの観点**は、ARTEX が実際に動いた(または侵害された中継)ホストで見えるものです。両者を混ぜないことが重要です。対象側で見える静的な指紋は限られており、行動の指紋が核心です。

### (ア)対象の観点: 自分のシステムに向けられたトラフィック

- **補強(enrich)照会の User-Agent `artex-enrich/1.0`。** ARTEX は資産を自動で補強(DNS・HTTP 確認)する際、この User-Agent で対象に直接 `GET` を送ります(`enrich/enrich.go`)。この経路は LLM とは無関係に ARTEX が自ら生成し、**リダイレクトを追わず、keep-alive を切り、応答の先頭部分だけを読んで `<title>` を抜き出す**という特徴があります。デフォルトの並行度は 4 です。したがって、`artex-enrich/1.0` UA による**短い接続・単発 GET・タイトルだけ読んで切断する**照会が複数の資産に同時に入ってきた場合は、ARTEX 系の補強トラフィックを強く示唆します。ただし運営者は UA を変更できるため、**不在が安全を意味するわけではありません。**
- **本攻撃トラフィックはツールのデフォルト指紋に従います。** worker は実際のツール(Bash で実行する外部ツール・HTTP)でリクエストを送ります。ARTEX はこのトラフィックを自前の記録プロキシ経由にするため、サブプロセスの環境変数に `HTTP_PROXY`・プロキシ CA パスを注入するだけで、**攻撃トラフィックに ARTEX 固有の User-Agent を強制しません。** そのため、対象が見る User-Agent・ヘッダーは**そのとき実行されたツールのデフォルト値**(各種コマンドラインツールのデフォルト UA)です。運営者がカスタマイズしていなければ一般的な自動化ツールの指紋が残り、カスタマイズしていれば通常のブラウザに偽装されることもあります。したがって、**単一の UA マッチングに頼らず、行動ベースの検知と組み合わせる**必要があります。
- **worker 内蔵の WebFetch ツールは `norma/0.4` User-Agent を残します。** 上記の Bash 実行の外部ツールとは異なり、ARTEX が norma SDK(`github.com/Autumn-27/norma`)で直接行う HTTP 照会(WebFetch ツール)は、その SDK のデフォルト User-Agent `norma/0.4` を攻撃段階に載せます。平文 HTTP でやり取りされるとき(または TLS 終端地点で)ネットワーク上で観測でき、[Suricata ルール sid 1000003](../detections/suricata/README.ko.md)がこの接頭辞(`norma/`)を捕捉します。ただしこの UA は ARTEX 固有ではなく、norma SDK を使う他のツールも使用するため、`artex-enrich/1.0` と同様に単独の証拠ではなく補助的な手がかりです。また Bash で実行されたツールはそれぞれの UA を使うため、**不在が安全を意味しません。**
- **内蔵のレートリミットがありません。** ARTEX 自体には対象トラフィック専用の速度制限がなく、リクエスト速度は LLM が動かす外部ツールが決めます。代わりに、タスクごとに worker がデフォルトで 3 つ並列に動くため、一つの対象に**複数の意図が同時に**進行することがあります。つまり「遅い単一セッション」としても「複数の角度からの同時進行」としても現れうるため、固定のしきい値一つでは捕捉しにくくなります。
- **行動シグネチャ(最も重要)。** 以下のパターンの**同時出現**が自律エージェントを示します。
  - 一つの発信元(または少数のローテーションする発信元)から、**偵察 → ディレクトリ・エンドポイント列挙 → パラメータ探針 → 認証・注入試行**が**短い間隔で連鎖**。
  - 同じエンドポイントに送りつつ、**応答コード・長さに反応して体系的に変形する**連続リクエスト(無作為なファジングではなく適応的)。
  - 人の運用時間帯を外れて**長時間途切れなく**続くセッション。
  - 失敗(401/403/429)の後も止まらず、**迂回の変形**を試みる執拗さ。

### (イ)運営者・フォレンジックの観点: ARTEX が動いたホスト

侵害調査で、中継・経由ホストに ARTEX がインストール・実行された痕跡を探すときの参考にします。

- **デフォルトのリスニングポート `:8787`。** ARTEX サーバーのデフォルト HTTP 受信アドレスです(`cmd/artex/main.go`、`--addr` で変更可能)。内部ネットワークのホストがこのポートに管理 UI(ダッシュボード・タスク・資産グラフ)を公開している場合は、ARTEX インスタンスを疑う根拠になります。
- **記録型 MITM プロキシ `127.0.0.1:8788`。** worker の Bash・HTTP 実行を横取りして全過程を記録するローカルプロキシのデフォルトアドレスです(`cmd/artex/main.go` の `--proxy` デフォルト値、ループバック専用)。独自の CA を生成して TLS を復号・記録するため(`mitmproxy-ca-cert.pem`)、ホストに **ARTEX がインストールした信頼 CA 証明書**があるか、そしてサブプロセスに `HTTP_PROXY`・プロキシ CA パスの環境変数を注入した痕跡があるかが手がかりになります。この注入は ARTEX が生成するすべての worker ツールに入り、変数名がソースにハードコードされているため(`agent/worker.go`)、**実行中のプロセスがプロキシ変数と mitmproxy CA 信頼変数を併せ持っているか**は、ポート一つよりも特異的な指紋です。[ホスト分類ツール](../detections/triage/README.ko.md)が `/proc`(またはフォレンジックイメージでは取得した環境変数ダンプ)からこの組み合わせを確認します。
- **self-update コールバック `artex-selfupdate`。** 自己アップデートが GitHub リリースを照会するときに使う User-Agent です(`selfupdate/`)。送信(egress)ログでこの UA によるコードリポジトリホストへのリクエストが見られれば、ARTEX バイナリの存在を示唆します。
- **PostgreSQL 上の二重グラフ。** `exploration_nodes`・`assets`・`companies`・`activity` などのテーブルと `agent_prompts` シードがある DB は、ARTEX データストアの特徴です。
- **DB ベースの正規表現承認ルールと監査ログ。** ツール呼び出しを評価する intercept ルールが DB に保存され、優先順位どおりに正規表現で評価されます(`intercept/`)。遮断された呼び出しは、監査ログ(`GET /api/audit`)に `【ARTEX 平台管控·非目标防御】` で始まる統制フレーミングとともに残るため、侵害ホストの監査記録にこの文字列が見られれば ARTEX の実行を裏付けます。
- **破壊的コマンドのハンティング指標。** ARTEX 自身のガードが遮断対象として内蔵するコマンドパターンは、そのまま自律エージェントが**試みうる**コマンド群の裏返しです。ホストのコマンド監査で以下をハンティング指標にしてください: `rm -rf`、`mkfs`、`dd of=/dev/`、`shred`/`wipe`、SQL `DROP DATABASE`/`DROP TABLE`/`TRUNCATE`、MongoDB `drop`/`dropDatabase`、Redis `FLUSHALL`/`FLUSHDB`、`curl`/`wget` の `-X DELETE`、そして `curl … | nc …` 類のデータ持ち出しパイプ。ただし最後のデータ持ち出しパイプは、データを破壊するコマンドではなく外へ持ち出す流出シグナルなので、性格が異なります。前の破壊パターンとは異なり、ARTEX のガードもこのルールだけはデフォルトでオフにしたまま内蔵しており(正当な点検用リバースシェルやデータ転送パイプでの誤検知が多いためです)、配布用の破壊コマンドハンティングルール([`destructive_command_hunting.yml`](../detections/sigma/destructive_command_hunting.yml))も破壊範囲に限定されていてこのパターンを含まないため、持ち出しパイプはすぐに遮断せず、別途ハンティング指標として置き、環境に合わせて調整してください。

> まとめ: **対象側の防御は行動指紋に賭け、静的 UA(`artex-enrich/1.0`・`norma/0.4` など)は補助的な手がかりとしてのみ**使います。運営者・フォレンジックの指紋(`:8787`・`127.0.0.1:8788`・`artex-selfupdate`・DB スキーマ・監査ログのフレーミング)は、**侵害された経由ホストを調査するとき**に有効です。

### IP アドレスのブロックはなぜ弱い第一次防御なのか

セキュリティインシデントが知られると、SNS やコミュニティに「攻撃 IP のリストを共有するのでファイアウォールで遮断してください」という投稿がよく出回ります。共有する側の善意とは裏腹に、**出所の不明な非公式 IP リストをそのまま遮断ルールに入れることはお勧めしません。** 自律型AI攻撃では特にそうです。

- **出所を検証しにくい。** 個人が投稿した非公式リストは、誰がどのような根拠で収集したのかを確認する方法がなく、インシデントと無関係な IP が混ざっていてもふるい分ける手段がありません。
- **すぐに古くなる。** 自律エージェントは VPN・クラウドインスタンス・乗っ取った中継サーバーを経由して、発信元 IP を頻繁に変えます(上記(ア)の「少数のローテーションする発信元」)。昨日観測された攻撃 IP は今日すでに捨てられている可能性が高く、リストを遮断しても攻撃者は別の IP で戻ってきます。
- **誤遮断のリスクが大きい。** リストに共有帯域・CDN・正常なクラウド IP が混ざっていると、その IP を遮断した途端に正常な顧客トラフィックや内部サービスまで一緒に切れてしまいます。自動遮断(下記第 6 節)と組み合わせると、誤遮断の被害がさらに速く広がります。

IP 遮断自体が無用だという意味ではありません。**公式の侵害指標(IoC)を対応機関や信頼できる脅威インテリジェンスから入手し、有効期間と誤遮断の可能性を検討したうえで適用する**場合に、初めて意味を持ちます。しかし IP 一行の遮断は、ローテーションする発信元を追いかける暫定措置にすぎず、長続きするのは変えにくい**行動**(第 2〜4 節の行動ベースの検知)と**攻撃対象領域の縮小**(第 3・5 節のハードニング: 公開資産の整理・パッチ・MFA)です。「指紋は変えられても行動は隠しにくい」というこのガイドの前提が、ここでもそのまま当てはまります。

## 3. 攻撃者が狙う侵入口とハードニング

自律エージェントは人間の攻撃者と**同じ弱点**を狙いますが、より速く執拗に繰り返します。以下は、防御の観点で優先すべきハードニング箇所です。

### 3.1 外部に公開された攻撃対象領域と既知(n-day)の脆弱性

自律エージェントが最初に、かつ最も安定して狙う侵入口は、巧妙なゼロデイではなく、**外部に公開されたままパッチが当たっていない、すでに知られた脆弱性**です。境界機器(VPN・ファイアウォール)、外部に開かれた管理・運用コンソール、アプリケーションサーバー・ミドルウェア・フレームワーク(例: 広く悪用される WebLogic・Struts 系)、そして**本サービスではなく提携・募集・従業員向けに付随した補助システム**が代表的な標的です。自律エージェントは資産グラフで公開面を自動的に列挙したうえで、公開エクスプロイト(PoC)が出回っている n-day を、**パッチが適用される前に**数百の資産に対して同時に狙います。公開された弱点を探して当てはめるこの過程の速度が、人間の攻撃者と非対称に開く点です。

- **攻撃対象領域を減らします。** インターネットに公開された資産・管理コンソール・補助システムのインベントリを継続的に維持し、外部に置く必要のないものは内部ネットワーク・VPN・許可リストの背後に移します。
- **既知の脆弱性を速やかにパッチします。** 境界機器・Web サーバー・アプリケーションサーバー・ミドルウェアの公開された脆弱性(n-day)は自律エージェントの第一の標的なので、公開 PoC が出回っているコンポーネントからパッチ適用の間隔を可能な限り短くします。どれから手をつけるかは、実際の悪用が観測された脆弱性を集めた [CISA KEV(既知の悪用された脆弱性)カタログ](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)を優先順位の入力とし、7.1 の国内勧告(KISA 保護ナラ)と照合してください。特定の CVE 番号を文書に固定するより、このように更新される公式リストを基準にすることで、自律エージェントが新たに出回る n-day へ標的を移しても後れを取りません。
- **公開が避けられないインターフェースを絞り込みます。** 外部に開いておかざるを得ない管理・運用インターフェースには、アクセス元の制限(IP 許可リスト)・MFA・VPN を加え、認証なしの列挙自体を防ぎます。
- **補助システムを本サービスと同じ基準で管理します。** 提携・募集・従業員向けの補助システムも、本サービスと同一のパッチ・監視水準で管理します。自律エージェントが食い込む入口は、本サービスではなくこうした補助経路であることが多いです。認証フロー自体のハードニングは次の 3.2 に続きます。

検知の観点では、特定の脆弱性の既知の経路(URL・パラメータ)を狙ったリクエストが外部から短い間隔で連鎖していれば、n-day スキャンのシグナルです。このシグナルは、第 2 節の行動指紋、第 4 節の同一発信元の多段階相関ルールと組み合わせたときに最もよく浮かび上がります。

### 3.2 補助的な認証・本人確認フロー

付加サービス・提携・募集チャネルのように、**本サービスとは別の経路で付随した認証・本人確認フロー**は、検証が緩いことが多く、迂回の標的になります。自律エージェントはこうした経路を自動的に列挙し、応答の違いを読んで体系的に迂回条件を探します。

- 本人確認・認証の段階を**本サービスと同じ強度**に統一し、迂回可能な補助経路を全数点検します。
- 認証状態の遷移(未ログイン → ログイン、一般 → 権限)を**サーバー側で再検証**し、クライアントが送ってきた信頼の目印(クッキー・ヘッダー・パラメータ)をそのまま信用しません。
- 本人確認トークン・ワンタイムコードの**有効期間・再利用・推測可能性**を点検します。

### 3.3 API の認証・認可(IDOR・権限昇格)

- すべてのオブジェクトアクセスに**サーバー側の所有権・権限チェック**を強制します(識別子を変えるだけで他人のリソースが開く IDOR を防ぎます)。
- 水平・垂直の権限昇格経路を列挙してみます。自律エージェントは識別子を機械的に増減させながら大量に試行するため、**単発の手動テストでは見逃した穴**をすぐに見つけ出します。

### 3.4 クレデンシャルスタッフィング(credential stuffing)

流出した ID・パスワードのリストを当てはめる攻撃は、自律エージェントが**速度と分散**で増幅します。

- ログイン・本人確認エンドポイントに**適応型レートリミット**(IP・アカウント・デバイス・行動ベース)をかけます。
- 機微な操作に**多要素認証(MFA)** を強制します。スタッフィングでパスワードが合っていても、二段階目の認証が防ぎます。
- **クレデンシャル侵害の検知**(既知の流出リストとの照合、異常なログイン位置・速度)で先制的に遮断します。
- ログインの失敗・成功の**分布の変化**(突然の低速・広範囲な試行)をアラートにします。

### 3.5 セッション・トークン・秘密情報の管理

- セッショントークンの**範囲・有効期間・更新**を最小化し、機微な遷移のたびに再認証します。
- API キー・内部トークンを応答・ログ・エラーメッセージに**露出させません**(自律エージェントはエラー応答から手がかりを積極的に収集します)。

## 4. 検知ルール・ログパターン(実務)

特定の製品に依存しない**疑似ルール**の形で記します。自分の WAF・IPS・SIEM の文法に置き換えて使ってください。以下のルールのうち、静的な指紋に基づくものは、すぐに配布できる [Sigma ルール(`detections/sigma/`)](../detections/README.ko.md)として提供しています。核心である行動・相関の検知(4.1・4.2)も単一のルールには還元できませんが、このうち ARTEX のコードで根拠を確認した行動指標は、配布可能な [Sigma 相関ルール(`detections/sigma/correlation/`)](../detections/README.ko.md)として提供しています(補強照会の速度・補強照会の対象数・ガード遮断バースト・ガードマーカーと破壊的コマンドの同一ホストでの同時発生)。ただし、その純粋な Web の多段階相関(列挙 → 探針 → 認証)のトラフィックは単一の ARTEX 固有 UA には還元できないため、環境ごとのベースルールが必要です。この相関は、下の 4.2 にすぐ配布を試せる汎用の行動ベース Sigma ベーステンプレートとして載せておいたので、自分の SIEM とベースラインに合わせて調整し、出発点として使ってください。ネットワーク層で平文 HTTP でやり取りされるとき(または TLS 終端地点で)観測される ARTEX の User-Agent は二つあり、どちらも [Suricata ルール(`detections/suricata/`)](../detections/suricata/README.ko.md)として提供しています。一つは enrich プローブの `artex-enrich/1.0`(存在シグネチャ sid 1000001・高速列挙の変形 sid 1000002)、もう一つは norma SDK の WebFetch ツールが攻撃段階で送る `norma/0.4`(sid 1000003)です。

### 4.1 WAF・IPS(行動ベース)

- 単一の発信元から**性質の異なるリクエスト群**(静的リソースのリクエストの割合は低く、列挙・パラメータ探針・認証試行の割合が高い)が**一つのセッションで**続く場合、スコアを上げます。
- 応答コード・本文の長さに**反応して変形される連続リクエスト**(エントロピーは高いが無作為ではない適応パターン)に重みを付けます。
- `artex-enrich/1.0` のような既知の自動化 UA は**即座に高リスク**とタグ付けしますが、UA の不在を安全と解釈してはいけません。

### 4.2 SIEM 相関ルール

- **同一発信元の多段階相関**: 同じ IP/ASN/セッションから (a) ディレクトリ・エンドポイントの列挙、(b) パラメータ探針、(c) 認証/注入試行が**短い窓の中ですべて**観測されたら「自律攻撃の疑い」アラート。
- **時間帯の異常**: サービスの通常のトラフィック分布から外れて**長時間途切れなく**続く単一セッション。
- **失敗後の継続**: 403/429 を受けても止まらず、**迂回の変形**を続ける発信元。

上記の**同一発信元の多段階相関**をすぐに配布して試せるベーステンプレートを、以下に置きます。攻撃トラフィックには ARTEX 固有の User-Agent がないため、このテンプレートは `detections/sigma/` の ARTEX ソースベースのルールとは異なり、**汎用の行動ベースのルール**です。特定の攻撃ツールの指紋ではなく、「一つの発信元が短い窓の中で列挙・探針・認証をすべて行う」という行動だけを見ます。三つの下位ルールと、一つのクライアントが時間窓の中で三つすべてを満たしたときだけ発火する temporal 相関ルールを、一つのファイルにまとめました。

### 4.3 認証ログ

- アカウント・IP ごとの**ログイン失敗率の急変**、広範なアカウントにわたる**低速分散の試行**(スタッフィング特有)、失敗から成功への**異常な遷移速度**。
- 本人確認・ワンタイムコードのエンドポイントに対する**列挙的なアクセス**。

### 4.4 送信(egress)・フォレンジック

- 内部ホストから `artex-selfupdate` UA でコードリポジトリホストに出ていくリクエスト。
- 内部で `:8787`(管理 UI)・`127.0.0.1:8788`(記録プロキシ)にバインドされたプロセス。
- `artex-enrich/1.0` UA で短時間に大量の外部資産を照会する DNS・HTTP 補強パターン。

## 5. ハードニングチェックリスト

防御組織がすぐに点検できるよう要約します。

- [ ] ログイン・本人確認・機微な API に**適応型レートリミット**を適用した(IP・アカウント・デバイス・行動)。
- [ ] 機微な操作に **MFA** を強制している。
- [ ] すべてのオブジェクトアクセスに**サーバー側の所有権・権限チェック**がある(IDOR の防止)。
- [ ] 認証状態の遷移を**サーバー側で再検証**し、クライアントの信頼の目印をそのまま信用しない。
- [ ] **補助・提携・募集チャネル**の本人確認の強度を本サービスと統一した。
- [ ] 流出した認証情報の**侵害検知・照合**を運用している。
- [ ] WAF を**行動ベースモード**で運用し、固定シグネチャだけに依存しない。
- [ ] **出回っている非公式の IP 遮断リストをそのまま適用せず**、公式の侵害指標(IoC)を信頼できる出所から入手し、有効期間・誤遮断リスクを検討したうえで反映する。
- [ ] SIEM に**同一発信元の多段階相関ルール**を入れた。
- [ ] 認証・アクセス・送信の**ログを十分な期間保存**する(自律攻撃は速いため、事後追跡の資料が重要)。
- [ ] インターネットに公開された資産・管理コンソール・補助システムの**インベントリを維持して攻撃対象領域を縮小**し、境界機器・アプリケーションサーバー・ミドルウェアの**既知(n-day)の脆弱性を速やかにパッチ**する。
- [ ] ネットワークの**セグメンテーション**で、横展開・権限昇格の被害範囲を減らした。
- [ ] 秘密情報(キー・トークン)を**応答・ログ・エラーメッセージに露出させない**。
- [ ] **自動遮断・隔離**の対応を準備した(人の承認だけを待っていては自律攻撃の速度に追いつけない)。

## 6. インシデント対応の要約

自律型AI攻撃の特徴は**速度**です。一人の人間が 1 年かけて行う侵入・持ち出しを、エージェントははるかに短い時間で完遂できます。対応の設計もこの速度を前提にします。

- **自動遮断を先制で。** 不審な発信元の隔離・セッションの無効化・レートの急減といった措置を、人の承認の前に**自動で発動**できるようにしておきます。すべてを人の承認ループに縛ると、攻撃の速度に追いつけません。
- **保存するログをあらかじめ決めておきます。** 認証ログ、アクセスログ(リクエスト本文を含められる範囲)、送信ログ、DNS クエリ。自律攻撃は痕跡を素早く積み上げるため、事後に攻撃チェーンを復元するにはこれらの資料が必要です。
- **侵害範囲を資産単位で追跡します。** 攻撃が資産グラフに沿って広がるため、最初に侵入された資産から横展開・権限昇格へとつながった**経路全体**を復元してこそ、再侵入を防げます。

### 6.1 不審なホスト・トラフィックの分類(triage)手順

ARTEX の関与が疑われるときに最初に確認すべきことを、順序に沿って整理します。第 2 節で指紋を二つの観点に分けたのと同じように、分類も **(ア)自分のサービスが標的になったか**と **(イ)特定のホストで ARTEX が動いたか**に分けて見ます。どの段階でも、一つの該当だけで断定せず、複数の指標と行動シグナルが一緒に現れるかで判断します。静的な指標がすべてなくても、行動シグナルが見えるなら調査を続けます。

**(ア)対象側: 自分のサービスが ARTEX の標的になったか**

1. アクセス・認証ログで、補強照会の User-Agent `artex-enrich/1.0` を検索します。リダイレクトを追わない単発の `GET` 照会が、短い間隔で複数の資産に同時に入ってきたかを確認します(第 2 節(ア))。運営者は User-Agent を変更できるため、該当がなくても次の段階に進みます。
2. 同一の発信元(または少数のローテーションする発信元)から出る**多段階の連鎖**を探します。偵察からエンドポイントの列挙、パラメータ探針、認証・注入試行へと短い間隔でつながり、応答コード・長さに適応し、401・403・429 の後も迂回の変形をやめない様相です。この行動シグナルは、静的な User-Agent よりも長く残ります(第 2 節(ア)の行動シグネチャ)。
3. SIEM を運用しているなら、この行動を [Sigma 相関ルール](../detections/README.ko.md)(補強照会の速度・対象数・ガード遮断バースト・ガードマーカーと破壊コマンドの同時発生)で仕掛けておき、検知された発信元を、上記「自動遮断を先制で」の原則に従って隔離・セッション無効化の対象に引き上げます。

**(イ)ホストフォレンジック: 特定のホストで ARTEX が動いたか**

不審なホストで次を確認します。指標の根拠は第 2 節(イ)と、機械可読の[侵害指標リスト](../detections/indicators/artex_indicators.csv)にあります。以下の五つの読み取り専用の点検のうち、前の四つ(リスニングポート・送信ログ・監査ログ・状態・記録ストア)は、[ホスト分類スクリプト](../detections/triage/)(`detections/triage/artex_host_triage.py`)が一度にまとめて実行してくれます。五つ目のコマンド監査は、破壊的コマンドが ARTEX 固有の指紋ではなく正当な管理者も使うハンティングの手がかりであるため、自動指標としては載せておらず、スクリプトでは実行せず、ホストのコマンド履歴から直接照合します。SIEM がなくシェルアクセスだけがあるときにまず実行し、それぞれの該当は以下の説明のとおり手がかりとしてのみ扱います。

1. **リスニングポート。** デフォルトのサーバーポート `:8787` とループバックの記録プロキシ `127.0.0.1:8788` が開いているかを、ホスト上で直接確認します。
   ```sh
   ss -ltnp | grep -E ':8787|:8788'   # ss がなければ netstat -ltnp を使います
   ```
   二つのポートは `--addr`・`--proxy` フラグで変更できるため、この照会が空でも、開いているポート全体と内部の管理 UI が立ち上がっているかを併せて確認します。
2. **送信ログ。** 自己アップデート User-Agent `artex-selfupdate` でコードリポジトリホスト(GitHub リリース)に出たリクエストが送信ログにあるかを確認します(`selfupdate/`)。このホストで ARTEX バイナリが動いたことを示唆します。
3. **監査ログ。** ガードの統制マーカー `【ARTEX 平台管控·非目标防御】` が監査記録にあれば、ARTEX の実行を裏付けます(`guard/guard.go`)。遮断されたツール呼び出しごとに、このフレーミングで残ります。
4. **状態・記録ストア。** ARTEX は PostgreSQL に探索グラフを置き(`exploration_nodes`・`assets`・`companies`・`activity` テーブルと `agent_prompts` シード)、実行ファイルの隣のデータディレクトリ(`cmd/artex/main.go` の `--data` デフォルト値)に状態と記録を残します。このディレクトリ直下には、タスクごとの成果物を収める `tasks/` と会話記録を収める `transcripts/` のサブディレクトリがあり、記録プロキシの成果物はその中の `traffic/` サブディレクトリに別途まとまります(`server/manager.go` がデータディレクトリ配下の `traffic/` を記録プロキシのストアとして開きます)。そのため、信頼 CA 証明書は `traffic/_ca/mitmproxy-ca-cert.pem`、トラフィックの索引は `traffic/_index/index.sqlite`、記録したリクエスト・応答の本文は `traffic/_blobs/` にあります。この三つが `tasks/`・`transcripts/` と一緒に見つかれば、記録プロキシが実際に動いたという状況証拠が強まります。
5. **コマンド監査。** 破壊的コマンドのハンティング指標(第 2 節(イ)末尾の `rm -rf`・`DROP DATABASE`・`FLUSHALL`・持ち出しパイプなど)を、ホストのコマンド履歴と照合します。正当な管理者も同じコマンドを使うため、手がかりとしてのみ扱います。

静的な指標(ポート・User-Agent・マーカー)は、運営者が変更または削除できます。したがって、**不在が安全を意味せず**、(ア)の行動シグナルと(イ)のホストの痕跡を併せて集めて判断することが、自律型AI攻撃の分類の核心です。

## 7. 国内の公式チャネル: 侵害指標・セキュリティ勧告と届出義務

国内の防御組織は、侵害指標とセキュリティ勧告を公式チャネルから受け取り、インシデントが起きたら法令で定められた届出義務を守らなければなりません。出回っている非公式リストの代わりに、以下の公式の出所を第一の基準にしてください。

### 7.1 侵害指標・セキュリティ勧告を受け取る場所

- **KISA(韓国インターネット振興院)の[保護ナラ・KrCERT/CC](https://www.boho.or.kr)** は、セキュリティ勧告と脆弱性の告知、侵害インシデントの対応情報を提供します。サイバー脅威情報分析・共有体系(C-TAS)で、機関間で脅威情報を共有します(C-TAS は加入機関間の共有体系であり、公開ポータルとは異なり、別途申請手続きを経ます)。
- **[金融保安院(FSI)](https://www.fsec.or.kr)** は、金融分野の侵害・脅威情報を業態横断で共有します(金融分野 ISAC)。金融業界であれば、このチャネルも併せて確認します。
- **[個人情報保護委員会](https://www.pipc.go.kr)** は、個人情報流出の届出基準と保護措置に関する告示・ガイドを公開しています。

第 5 節のハードニングチェックリストにある「公式の侵害指標を信頼できる出所から入手する」が指す出所が、まさにこれらのチャネルです。公式の侵害指標であっても、有効期間と誤遮断リスクをまず検討したうえで反映するという原則は、第 2 節の「IP アドレスのブロックはなぜ弱い第一次防御なのか」で説明したものと同じです。

### 7.2 国内法上の届出義務

自律攻撃は急速に広がるため、第 6 節のインシデント対応手順の中に、法定の届出段階をあらかじめ入れておいてください。以下は要点であり、正確な適用対象と期限、要件は、各機関の最新の告示で確認する必要があります。

- **個人情報の流出**: 「個人情報保護法」第 34 条に従い、流出を認知したときから 72 時間以内に個人情報保護委員会または KISA に届け出て、情報主体に通知します(情報主体 1 千人以上、機微情報や固有識別情報の流出、外部からの不正アクセスによる流出などが届出要件に該当します)。
- **侵害インシデント**: 「情報通信網利用促進および情報保護等に関する法律」に従い、情報通信サービス提供者は、侵害インシデントを認知してから 24 時間以内に科学技術情報通信部と KISA(KrCERT/CC)に届け出ます。
- **金融会社**: 金融分野の監督規定に従い、金融監督院や金融保安院など所管機関に別途報告しなければならない場合があるため、該当する規定も併せて確認してください。

実際の届出は、侵害インシデントの場合は[保護ナラ](https://www.boho.or.kr)または市外局番なしの 118(KISA サイバー民願センター)で、個人情報流出の場合は個人情報保護委員会の[個人情報ポータル](https://www.privacy.go.kr)で受け付けています。届出期限が短いため、担当者と連絡経路を第 6 節のインシデント対応手順にあらかじめ書いておいてください。
