# 脆弱性の複数トラフィック証拠

> この文書は、アップストリーム(原本)ARTEX の設計文書を日本語に翻訳したものです。脆弱性とトラフィック証拠を関連付ける
> 機能の設計を、コントリビューター・メンテナー向けにまとめています。原文(中国語)は
> [`finding-traffic-evidence-zh.md`](finding-traffic-evidence-zh.md) に保存されています。
>
> English: **[Vulnerability multi-traffic evidence (finding-traffic-evidence-en.md)](finding-traffic-evidence-en.md)**.

脆弱性詳細画面の「関連付けられたトラフィック」は、複数ページにわたる複数選択、用途と説明の入力、並べ替え、バインディングの解除をサポートします。トラフィックページでも、複数のレコードを一度に選択して、既存の脆弱性 1 件に関連付けられます。タスクが継承した脆弱性の証拠は読み取り専用であり、変更するには元のタスクに入る必要があります。

システム設定の「Agent 自動トラフィックバインディング」はデフォルトでオフで、読み取り・変更のインターフェースは `/api/settings` の `agent_traffic_binding` です。この機能をオンにすると、リクエスト/レスポンスの参照、ツール呼び出し、プロンプトに由来する Token の消費が増え、次のラウンドの Agent から新しい設定が使われます。オフのときは、自動バインディングのパラメーターと補完バインディングのツールを隠し、自動バインディングの案内を注入せず、すでに実行中のセッションが新たに送信する自動バインディングを拒否します。手動バインディング、トラフィックのキャプチャ、保存済みの証拠の読み取りとエクスポートは影響を受けません。

機能をオンにしたあとの基本的な流れは、「発見事項の保存 → レポート Agent の自動トリガー → トラフィックの突き合わせ・バインディング → 最新の証拠バージョンでレポートを作成」です。報告者は `evidence` に、検証コマンド、主要な出力、すでに取得済みの実際のトラフィック ID と用途を残します。レポート Agent は脆弱性の詳細と実行履歴を総合し、`traffic_search` / `traffic_get` で確認してから `bind_finding_traffic` を呼び出し、最新の `version` を読み取ってレポートを保存します。スイッチをオフにすると、レポート Agent は元のトラフィックの検索/読み取りツールを追加で受け取らず、自動バインディングも行いませんが、それでも手動でバインディングしたスナップショットを読み取ってレポートを生成できます。

既存の呼び出し元とも互換性があります。`report_finding` の `traffic_refs` / `evidence_hint_id` で、引き続き明示的に即時バインディングできます。バインディングは任意です。TCP のような非 HTTP の脆弱性である場合、まだ収集していない場合、または正確なレコードが見つからない場合は、参照を省略しても通常どおり報告し、レポートを作成できます。コマンド出力やログなど、検証可能な他の証拠は残し、バインディングしなかった理由もあわせて説明することを推奨しますが、必須の入力フィールドは新たに追加しません。送信した ID はすべて有効で、本文が完全でなければなりません。そのうち 1 つでも失敗すると、今回のバインディング操作全体をロールバックします。報告と同時に明示的にバインディングしていて失敗した場合は、報告全体をロールバックします。同じスナップショットを重複して追加しても、バインディングは増えず、説明も上書きされません。

## Agent ID 体系とレポートバージョン

`report_finding` に任意のパラメーターを新たに追加しました。配列の順序がそのまま初期の証拠の順序になります:

```json
{
  "traffic_refs": [
    {"traffic_id": "実際のトラフィック ID", "role": "baseline", "note": "正常アカウントのリクエスト"},
    {"traffic_id": "別の実際のトラフィック ID", "role": "proof", "note": "再現リクエスト"}
  ]
}
```

用途は `baseline`(正常な対照)、`proof`(脆弱性の証明)、`verification`(補完検証)、`supporting`(補助証拠、デフォルト)です。まず `traffic_search` / `traffic_get` で実際のレコードを突き合わせます。ドメインと時刻は候補を絞り込む用途にのみ使い、タスクへの帰属を断定しません。

プロンプトは [CyberStrikeAI の脆弱性報告ツールの案内](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go) を参考にしており、このプロジェクトの任意バインディングの規約と組み合わせつつ、バインディングしなかった理由を必須で検証するルールは設けていません。ID を推測してはならず、単に証拠を埋めるために繰り返し検知してもいけません。

戻り値の 1 行目は、これまでどおり `finding recorded: <探索ノード ID>` です。続く JSON は、独立した脆弱性レコードの `finding_id`、探索ノードの `finding_node_id`、バインディングの要約を提供します。

- `get_finding_traffic(finding_id)` は**独立した脆弱性レコード ID** を使用し、順序付きの一覧と `version` を返します。`binding_id`、`side=request|response`、`offset`、`length` を渡すと区間ごとに分けて読み取れ、1 区間は最大 8192 バイトです。
- `update_finding_report` の `finding_id` は、**引き続き探索ノード ID を使用します。** 新たに追加した `evidence_version` には、実際に読み取ったバージョンを入れます。レポートを生成している間に証拠が変更された場合は古いバージョンでの書き込みを拒否するため、再度読み取ってから生成する必要があります。
- 古いレポート呼び出しがバージョンを渡さない場合は、既存のトラフィック証拠を上書きしたとは表示しません。バインディング、説明、用途、並び順が変更されると、既存のレポートに更新が必要である旨の表示が付きます。

自動バインディングをオンにすると、`add_hint` / `add_task_hint` が、単一のヒントまたは一括 `hints` の各要素に `traffic_refs` を保存することをサポートします。プランナーが代理で報告する場合は `evidence_hint_id` を渡すことで、このタスクに属するヒント内の参照を明確に選択でき、継承したヒントは参照できません。システムは、ドメイン、時刻、参照履歴からバインディングを推測しません。送信が失敗した場合は、一部だけが作成された脆弱性を生成せず、レポートを前倒しでトリガーすることもありません。

既存の脆弱性でバインディングが欠けている場合は、`bind_finding_traffic(finding_id, traffic_refs)` で補完バインディングでき、再登録する必要はありません。`list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail` は、明確な `finding_id` と `finding_node_id` を返し、従来の `id` は探索ノードの意味を維持します。

起動時には、古いツール schema に任意のプロパティを追加するだけで、元のデフォルトのトラフィックツールバインディングをレポート Agent まで拡張し、補完バインディングツールはデフォルトでレポート Agent に任せます。ユーザー定義のバインディング一覧、プロンプト、説明、有効化状態はそのまま維持します。案内は、最終的なツールの組み立てが完了したあとにまとめて追加します。報告ロールは取得済みの証拠を引き渡す役割を担い、レポート Agent は突き合わせ・バインディング・レポート作成を担います。プラットフォームの会話にタスクのコンテキストがない場合は、構造化されたヒントでタスク Agent に引き継ぐ必要があり、直接報告しません。タスクの完了を判定する前に、まず既存の証拠を引き渡す必要があり、バインディングするトラフィックがない場合は待機を強制しません。失敗した `report_finding` は、レポート Agent をトリガーしません。

## API

基本パスは `/api/exploration/findings/{finding_id}/traffic` で、独立した脆弱性 ID を使用します。認証は既存の方式にそのまま従い、`context_task` がタスクの可視性と継承時の読み取り専用かどうかを検証します。

メソッドと相対パスごとのリクエスト・戻り値は次のとおりです:

- `GET`: 順序付きの要約、証拠バージョン、レポートが採用したバージョンを返します。
- `POST`: `{"traffic_refs":[...]}` を一括で追加します。
- `PATCH /{binding_id}`: `{"version":1,"role":"proof","note":"説明"}` で変更します。
- `DELETE /{binding_id}`: `{"version":1}` で削除します。
- `PUT /order`: `{"version":1,"binding_ids":["2","1"]}` で並べ替えます。完全な一覧でなければなりません。
- `GET /{binding_id}`: スナップショットのメタデータと、長さが制限された本文のプレビューを返します。
- `GET /{binding_id}/body`: `side`、`offset`、`length` を受け取り、`download=1` の場合は完全な元のバイト列をダウンロードします。

バージョン/並べ替え集合の競合やアーカイブ進行中の書き込みは `409` を返し、継承項目への書き込みは `403` を、存在しない、または当該脆弱性に属さないバインディングは `404` を返します。トラフィック/添付ファイルの読み取りと検証が失敗した場合は、明確にエラーを返します。

## 保存とマイグレーション

起動時に PostgreSQL に対して冪等なマイグレーションを実行します。`traffic_evidence_snapshots`、`finding_traffic_bindings` テーブルと、`findings.evidence_version` / `report_evidence_version`(デフォルト値 0)カラムを新たに追加します。過去のテキストを根拠に補完バインディングを推測することはしません。

スナップショットは、元のトラフィック ID、取得時刻、URL、メソッド、ステータス、リクエスト/レスポンスヘッダー、本文の長さ、SHA-256 を保存します。本文はハッシュに従って `<data>/evidence/blobs/<先頭 2 桁>/<hash>.bin` に保管し、クリーンアップ対象の `data/traffic` とは分離されているため、複数の脆弱性でスナップショット/本文を共有できます。スナップショットは内容の更新インターフェースを提供せず、検証が一致しない場合は、読み取りとエクスポートが失敗します。

元のトラフィックの書き込みロックのもとで、大きな本文の blob や古いディレクトリレコードを含め、本文全体を読み取ります。まずファイルを永続化して検証したうえで、1 つの PostgreSQL トランザクションで探索ノード、意図の関係、脆弱性、スナップショット、バインディングを記録し、コミットしてからプランナーに通知します。失敗した場合、参照されないファイルが残ることはありますが、一部だけが記録された業務レコードは作られません。

PostgreSQL の advisory lock `7337741004` が、証拠ファイルと SQL の参照を調整します。タスク行ロックは、アーカイブ待ち行列に入れたあとの証拠の変更を禁止します。復元は、本文の配置からメタデータのコミットまで、全過程で証拠ロックを保持します。脆弱性を削除すると、バインディングも連鎖して削除されます。

クリーナーは毎時実行され、参照がなく進行中でもないタスクの内容だけを回収しますが、最低でも 24 時間は遅延させます。通常のトラフィックのクリーンアップは、証拠ディレクトリには触れません。ホットデータをバックアップする際は、PostgreSQL と `data/evidence` をあわせてバックアップします。

## エクスポートとアーカイブ

Markdown には順序付きの証拠一覧とバージョンが入り、JSON にはメタデータが、CSV には件数とバインディング ID が追加されます。`md-zip` は、脆弱性の Markdown を維持しつつ、次の構造もあわせて提供します:

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown は相対リンクでパケットを参照します。ダウンロードを送信する前に、添付ファイルのコピー、ハッシュ検証、圧縮、ディスク同期、そしてすべての ZIP エントリの CRC 読み取り検証を完了します。エントリが欠けていたり破損していたりする場合は、ダウンロード全体が失敗します。完全な添付ファイルは、バイナリの元のバイト列をそのまま保持します。

アーカイブ v3 は、脆弱性のバインディング関係に従ってスナップショットと本文を収集し、元のトラフィックやドメインに依存しません。パッケージの検証を完了してから初めてホットデータをクリーンアップし、共有されている証拠は引き続き保持します。復元は、先に配置した本文を検証してから、トランザクションでメタデータとバインディングを復元し、失敗した場合は再試行をサポートします。v1/v2 も引き続き復元でき、欠けている新しいフィールドは明示的に 0 で埋めます。

## 検証と境界

テストパッケージごとに、独立して新規作成した PostgreSQL テストデータベースを用意して `ARTEX_PG_DSN` で指定し、残っているタスク/モデルのフィクスチャがバックグラウンド実行をトリガーしないようにします。関連パッケージの全テストを実行し、設定の不足によってスキップされたテストがないことを確認します:

```sh
# 各パッケージを実行する前に、ARTEX_PG_DSN を該当する独立したテストデータベースに設定します。明示的な設定が失敗した場合は、必ずエラーを出す必要があります。
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

フロントエンドの検証には、`npx tsc --noEmit`、影響を受けたファイルの Biome チェック、Webpack ビルド、`NEXT_EXPORT=1` による静的エクスポートが含まれます。独立したキャッシュディレクトリを使用して、実行中の開発サーバーを上書きしないようにします。

ローカルのエンドツーエンド受け入れ検証は、独立したポート、制御された HTTP / ドメイン HTTPS の対象、一時的なデータディレクトリを使用し、2 種類のバインディング入口、複数ページにわたる選択、並べ替え/説明、エラー案内、継承時の読み取り専用、ダウンロードを対象とします。さらに、元のトラフィックを削除したあとのエクスポート、アーカイブ、ホット本文の回収、復元とハッシュ検証まで含みます。

最初のバージョンは、グローバルな証拠調整ロックを使用します。大量のバインディング/エクスポートや、低速な添付ファイルのダウンロードが進行している間は、他の証拠操作が待機することがあります。録画されたレコードや完全な本文がない場合、証拠をでっち上げることはできません。この機能はキャプチャのスイッチを変更せず、HTTPS で IP に直接アクセスする際の証明書の問題も扱いません。
