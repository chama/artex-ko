# サイドクエスチョンの長文会話とコンテキスト予算

2026-09-11 修正。以前の実装は、リクエスト JSON の文字数をそのままトークン数とみなし、メインタスクの 32K の出力予約量をそのまま引き継いでいたため、HTML・JS・ツール結果が多い場合に、正常なサイドクエスチョンを事前に拒否してしまう問題がありました。

## オープンソース実装との対照

- [Grok CLI のサイドクエスチョンコンテキスト](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/agent.ts#L739): 直近のユーザー・アシスタントのテキストから一部の断片を抜粋します。文字数の予算は約 2000 文字で、1 件あたり最大 400 文字で切り詰めます。この経路では、連続したサイドクエスチョンの問答履歴を保持しません。
- [Grok CLI の独立リクエスト](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/utils/side-question.ts): キャンセルシグナルを別に持ちます。モデルが対応していれば、出力上限は 2048 トークンです。ツールは提供しません。
- [Grok CLI のメインセッション圧縮](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/compaction.ts): トークンを推定し、直近の内容を残し、新しい内容を以前の要約に反映し、ターン境界をまたぐ切り詰めを処理します。
- [OpenCode のセッション圧縮](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/compaction.ts): リクエスト全体を推定し、出力・バッファを予約し、直近の内容にローリング要約を加え、ツールなしの要約リクエストを送ります。この実装は、デフォルトで直近の予算 8000、要約出力の上限 4096 トークンを使います。
- [OpenCode のオーバーフロー復旧](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/runner/llm.ts): アシスタントの出力がまだ始まっていないときにだけオーバーフロー復旧を試み、復旧後の呼び出しは同じオーバーフロー復旧経路に再び入りません。

ARTEX は、独立した出力予算、直近の内容とローリング要約、制限付きの復旧という方式を参考にしました。norma v0.3.6 の構造化メッセージとツールのペアリングはそのまま維持しつつ、Grok のテキスト抜粋方式はそのまま採り入れておらず、OpenCode のメインセッション圧縮イベントを ARTEX のメイン transcript に記録することもしません。

## リクエスト予算と実行

- メッセージは norma の方式をそのまま使い、コンテンツブロック単位で UTF-8 バイト数を推定して 4/3 の余裕分を加えます。これに加えて、システムプロンプト、ツール schema、メッセージのラッピングオーバーヘッドも計上します。この推定値は、モデルの正確なトークン数ではありません。
- サイドクエスチョンの出力は、デフォルトで最大 8192 トークンで、メイン設定にすでに定められている出力上限も超えません。サービスの環境変数 `ARTEX_BTW_MAX_OUTPUT_TOKENS` で 256–32768 の範囲の上限を設定でき、製品のデフォルトモデルやメインタスクのパラメーターは変更しません。
- 入力予算は、コンテキストウィンドウから出力上限と安全マージンを引いた値で、ウィンドウサイズが不明な場合はプラットフォームのデフォルトである 200K を使います。安全マージンはウィンドウの 5% で、最小 128 トークン、最大 8192 トークンです。
- 成功した問答は、増加する連番に従って、1 回あたり最大 20 組まで読み込みます。原文は最大 20 組まで残し、そのトークン予算は入力予算の 1/4 以内で、16K を超えません。
- 予算を超えた問答は、ローリング要約として反映します。要約には、出典の記録とコンテキストの時点をあわせて含めます。過去のアシスタントの回答は新しいツールの証拠と同等ではないため、矛盾が生じた場合は最新のメインスナップショットを優先します。
- メインコンテキストがそれでも長すぎる場合は、コピーの古いメッセージだけを要約し、直近の内容は最大 8K トークンまで残します。切る位置は、ツール呼び出しとその結果を分断しません。1 つのまとまりが大きすぎる場合は、そのまとまり全体を要約に入れます。
- 要約の入力は、実際に残っているウィンドウサイズに合わせて UTF-8 基準で安全に分割し、出力上限は 2048 トークンです。空の要約、切り詰められた応答、ツール呼び出し、要約予算の超過は、いずれもキャッシュに書き込みません。1 回のサイドクエスチョンで要約の呼び出しは最大 12 回で、同じ 120 秒のタイムアウトを共有します。上限に達した場合は、無限に繰り返さず、明確に失敗として終了します。
- モデルが初めてコンテキスト超過を返し、まだテキストやツール呼び出しを出力していない場合は、さらに縮小したうえで最大 1 回だけ再試行します。推定サイズが小さくならなければ、復旧を直ちに停止します。それ以外のモデルエラーや、一部だけストリーミングされた出力では、この復旧は起こりません。
- 要約、失敗した試行、キャンセル時点の使用量を含め、すでに集計されたすべての使用量は、同じサイドクエスチョンのリクエストに累積します。Provider が使用量を返さない場合は 0 として記録するだけで、推定値を実際の使用量であるかのように偽装しません。

## 永続化と画面

`side_question_sessions.memory` には、古い問答の要約、反映済みの連番(ordinal)、そしてスナップショットの識別ごとにキャッシュしたメインコンテキストの要約を保存します。`side_question_requests.context_info` には、準備段階、実際に再度載せたまとまりの数、要約の使用内訳、予算の推定値を保存します。

要約は、元のリクエストがまだ実行中で、クリアバージョンが一致する場合にのみ保存します。クリアはキャッシュも一緒に消去し、遅れて到着した書き込みが、すでにクリアされたデータを復活させることはありません。新しいスナップショットは、以前のスナップショットの要約を再利用しません。要約フィールドは v3 のタスクアーカイブとともに保存し、フィールドのない古い v3 を復元する際は空のオブジェクトで補い、v1・v2 とも引き続き互換性があります。

POST はリクエストを先に受け付けて返し、準備と圧縮はバックグラウンドで実行し、受付ロック(admission lock)やデータベーストランザクションは保持しません。SSE と履歴画面には、準備、問答の整理、コピーの圧縮、応答の各段階が表示されます。圧縮の失敗は、該当するサイドクエスチョンのリクエストの失敗終了状態として保存します。フロントエンドはエラーを残し、今回失敗した質問の下書きを復元し、フローティング通知で入力欄を覆いません。履歴のポーリングも、送信エラーを消去しなくなりました。
